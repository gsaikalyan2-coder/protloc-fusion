## 4. Partitioning and determinism

Identical sequences are collapsed to one representative (the smallest accession) before
GraphPart, so they cannot land in different partitions; every accession inherits its
representative's partition and cluster, and a removed representative removes all its
accessions.

Two runs of `graphpart mmseqs2needle ... --threads 6 --prefilter` on the same FASTA, in
parallel:

| Run | Wall time | Edge stage | Accessions removed | Registry SHA-256 |
|---|---|---|---|---|
| A | 3,211.3 s | 3,063.8 s | 1,588 | `c8025920edce73815f345c6c0a306e769acb8a24c56ad4dae9270d9433bb5547` |
| B | 3,215.1 s | 3,066.1 s | 1,595 | `22d917bada487e5a68b7b4372931fdecd8c65ea71ff575e1238443fc22c3bc6b` |

**These differ.** The two runs found the identical 208,762 edges (sorted `edges.csv` files
have the same MD5), and only the order of the edges differed. GraphPart's partitioning
depends on edge order, and the threaded alignment step does not emit a canonical order.
`graphpart.csv` differed in 11,774 of 33,325 shared accessions.

Protocol adopted: sort the saved edges (`LC_ALL=C sort -t, -k1,1 -k2,2`), then run
GraphPart's own `precomputed` mode on them (`-th 0.30 -tf one-minus -pa 5`) with
`PYTHONHASHSEED=0`. Measured in WSL, four runs in parallel (222 to 226 s each):

| Variant | `graphpart.csv` SHA-256 |
|---|---|
| sorted edges, hash seed 0, run 1 | `75ea2803e31eeaa9d6333ed5d016f7a5e514d00830155a93c824c8972de4eb07` |
| sorted edges, hash seed 0, run 2 | same |
| sorted edges, hash seed 7 | same |
| edges shuffled, hash seed 0 | `e29869204f6d173bed3339088ca5aa7f25ef2d7e59caf95f48c1f03f1930468e` (differs) |

So determinism holds for a **fixed edge order**, and not otherwise. Two scratch directories
(`det_1`, `det_2`) were built from runs 1 and 2: pre-repair registry SHA-256
`c71c7725d535f68b5af5caff7f1681b1687df113b0f109fea8acff87f600d1d9` in both (1,557
accessions removed); after the repair of §5, `37ca5e05…276a` in both. Recorded in
`data/manifests/split_manifest.json`. A first try with `-th 0.70` was a wrong threshold
direction (zero removals); it is not used anywhere.

`cluster_id` is the connected component of edges above 0.30 identity from GraphPart's
checkpoint (`edges.csv`), numbered by smallest member, `C%07d`: 12,598 clusters. GraphPart's
output column `cluster` is the **partition**, not a homology cluster.

Removal: GraphPart removed 1,497 of 34,965 distinct sequences (1,557 accessions). That is
4.39% of the 35,443-record working set, well under ADR-0002's 15% revisit trigger. The
`needleall` runtime trigger (a working day) was not reached for this set.

## 5. Leakage gate

`scripts/leakage_check.py` recomputes leakage from the corpus and the registry; it never
reads GraphPart's output. It writes its own FASTA, runs its own `mmseqs easy-search`
(sensitivity 8.0, 5,000 hits per query, `--min-seq-id 0.25`, identity over the shorter
sequence, local alignment), and hashes sequences itself. Stage 2 re-scores every cross-partition
candidate above 0.30 by global alignment with EMBOSS `needle` (identical residues over
alignment length, gap open 10, extend 0.5, EBLOSUM62, protein typing forced), the definition
ADR-0002 and GraphPart use. **The gate counts stage 2.** The local score alone is not the
ADR's metric: a 13-residue peptide can match 10 residues locally (0.769) and be nowhere near
30% globally. Exit 1 on any leakage.

Unit tests: `backend/tests/unit/test_leakage.py` (10).

**Failing on a toy leak first.** `scripts/leakage_check.py --toy leaked`: four real corpus
sequences (HBA_HUMAN P69905 and HBA_MOUSE P01942, real orthologs, and two accessions that
share one real sequence, A0A017SP50 and A0A2D1VNJ8), put in different partitions by hand:
`FAIL: duplicates 1, search clusters 2 ... cross-partition pairs 2`, exit 1; the human/mouse
pair scored 0.859 global identity. `--toy clean` (same sequences, grouped): `PASS`, exit 0. No
sequence is invented.

**Real split, first run (pre-repair registry `c71c7725…`).** MMseqs2 search 07:14:44 to
08:00:34 (45 min 50 s, 12 threads): 0 duplicates, 0 registry clusters, **7,232 local
candidates**. Stage 2 (58 s) confirmed **7 pairs above 0.30 global identity, 7 clusters**:

| Pair | Partitions | Global identity | Lengths |
|---|---|---|---|
| P0C1M2 / P0C1M3 | 1 / 2 | 0.769 | 13 / 13 |
| P0DQW5 / P86131 | 1 / 5 | 0.438 | 16 / 15 |
| P0DUT5 / P0DX48 | 1 / 5 | 0.378 | 37 / 33 |
| P0C8D3 / P0DUU7 | 4 / 1 | 0.333 | 15 / 12 |
| D0PX85 / P0DRL4 | 2 / 1 | 0.329 | 73 / 65 |
| D4B2Q8 / K1XW16 | 2 / 4 | 0.326 | 186 / 167 |
| C0HJV3 / C0HJV5 | 5 / 3 | 0.301 | 69 / 79 |

GraphPart's MMseqs2 prefilter missed them. Saved as `data/manifests/leakage_report_pre_repair.json`.
Two earlier attempts at stage 2 failed for my own reasons and are not evidence: a crash when
EMBOSS guessed an 11-residue peptide was nucleotide (fixed with `-sprotein1 -sprotein2`).

**Repair (you chose it, option 1).** `scripts/split.py repair` removes one member of each leaking
pair: the one in the larger partition (size counted before any drop), ties to the later accession,
together with any accession sharing its sequence. It dropped 7 accessions (no twins). Partition sizes moved by at most 5 (9,378 / 6,061 / 6,008 / 5,885 / 6,554 before, 9,373 / 6,060 / 6,008 / 5,885 / 6,553 after). Run on both determinism directories: same
result, `37ca5e05…276a`.

**Real split, repaired registry.** Rechecked against the saved MMseqs2 hits (no new search, 65 s):

`PASS: duplicates 0, search clusters 0, registry clusters 0, cross-partition pairs 0`, exit 0.
Local candidates now 7,205; none above 0.30 global identity. Report:
`data/manifests/leakage_report.json`, `passed: true`, registry SHA-256 `37ca5e05…276a`.

Limits, stated plainly: a search is a heuristic and cannot prove absence. The zero means no
pair above 0.30 global identity was found among candidates the checker's search surfaced
(sensitivity 8.0, 5,000 hits, local identity at least 0.25). The recheck reused the pre-repair
search results, so it shows the 7 pairs are gone; it does not search again. A pair missed by both
GraphPart's prefilter and this search would not be seen.

All records are group `eukarya`, all with annotated localization (this is the working-set

sequences each before removal and 8,728 / 6,084 / 6,021 / 6,120 / 6,481 after it, and the frozen

**The calibration split must respect the same clustering** (PROJECT_PLAN §4 note). Any
calibration or validation set drawn from the training partitions has to be formed from
whole homology clusters, using the registry's `cluster_id`, never by drawing random
sequences. Otherwise calibration data shares homologs with training and the calibrated
confidence is optimistic. The split manifest records this rule.

## 8. Deviations

1. **Working set narrowed to ECO:0000269 eukaryotic localization** (§3), reversing your earlier rule.
2. **Determinism protocol.** Raw `mmseqs2needle` runs are not deterministic (§4); the frozen
   registry comes from GraphPart `precomputed` mode on canonically sorted edges with a fixed hash seed.
   The edges still come from the `mmseqs2needle` backend.
3. **Two-stage gate.** The gate counts global identity; local candidates are reported beside it (§5).
4. **Leakage repair.** 7 accessions removed after GraphPart, by a recorded deterministic rule (§5).
   The pre-repair report and registry hash are kept.
5. **`alignment_backend` reconciled** from the stale `needleall` to `mmseqs2needle` in the data config.
6. `cluster_id` derived from checkpoint edges, because GraphPart's `cluster` column is the partition.
