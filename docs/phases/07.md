Branch `phase/07-embedding-cache`, from `phase/06-graphpart-splits`.
Spec: `PROJECT_PLAN.md` §4 row 7. Every number below comes from a command run in this phase;
what was not measured is under UNVERIFIED (§9). **The full cache was not built.** A

## 4. Long-sequence policy

Sliding window, chosen by you: 1022-residue windows, start step 511, last window moved back to
end at the sequence end, overlapping residue states averaged, then mean-pooled. Nothing is
truncated or excluded (`excluded: 0` in the manifest). 31 of the 500 cached sequences are windowed.

## 6. Determinism

| Check | Result |
|---|---|
| Padding: one sequence alone vs in a batch, six sequences | max absolute difference 9.54e-07 |
| Same sequence in two separate processes | identical bytes (hashes in §1) |
| Real kill after the first committed shard, then resume (64 sequences, shards of 4) | interrupted before completion; no `.tmp` left; resumed shard-index hash equals the uninterrupted one |
| CPU vs CUDA | not measured: no GPU was used |

Padding differences are float rounding, not identity: batch composition is fixed by the input,
so the cache is byte-reproducible, but a vector can differ at the 1e-6 level if the batch changes.

## 8. Deviations

1. **Subset, not the full cache.** You needed to move on within an hour; the full CPU run is
   about 19 h (estimate). `scripts/embed.py --pack`, `--bundle` and `--input` exist so the full run
   can be done on a free GPU without the 1 GB corpus; it was not run. The manifest says `subset`.
2. **Windows native, not WSL**, for the reason in §2.
3. **Extra modes** beyond the plan: `--pack`, `--bundle`, `--input`, `--subset`.
4. **Two `--measure` runs.** The first predates provenance recording; the manifest uses the second.
5. **Per-residue storage not cached**, recorded in ADR-0009 §2.7 instead of silently dropped.

## 9. UNVERIFIED

- The full 33,461-sequence extraction, its total time and its cache size.
- Any GPU result, and the CPU-vs-GPU difference. Byte identity holds only for this machine, device
  and torch build.
- That sliding-window vectors are good: no comparison to a reference implementation or to
  downstream accuracy (Phase 9 measures that).
- That the 500-sequence subset is representative by class; only length and partition were looked at.
- The torn-write case (a kill during a write) is covered by a unit test, not by the real kill,
  which stopped between shards and left no temporary file.
- Frontend gate, Docker and GitHub Actions: nothing there changed and none was run.
